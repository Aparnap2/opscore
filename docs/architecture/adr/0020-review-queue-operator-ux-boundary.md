# ADR-0020: Review Queue and Operator UX Boundary

## Status

**Accepted** — review queue REST endpoints exist at `GET/POST /admin/review-queue`. Slack Block Kit integration is implemented. Streamlit admin UI is under development.

## Date

2026-07-13

## Context

### Problem Statement

OpsCore operators need to review and act on human-in-the-loop (HITL) requests generated by agent workflows. These requests include vendor approvals, document review, compliance gap confirmation, and fraud flag reviews.

Currently, operators interact with the system through:
1. **Slack Block Kit** — interactive Approve/Reject buttons in Slack messages.
2. **Admin API** — `GET/POST /admin/review-queue` endpoints.

However, the operator UX is not fully defined:

1. **No dashboard.** Operators cannot see a summary of all pending requests, their priority, or their SLA status at a glance. They must rely on Slack notifications or query the API manually.
2. **No audit trail for operator decisions.** The Admin API records the decision (APPROVED/REJECTED) but does not capture who made the decision, their role, or their reasoning.
3. **No notification on new pending requests.** Operators are notified via Slack for each HITL request, but there is no dashboard-level notification or badge count.
4. **No SLA tracking.** There is no metric for time-to-decision — how long operators take to respond to HITL requests.
5. **No history view.** Operators cannot see past decisions for a vendor or document without querying the audit trail directly.

### Current State

| Interface | Implemented | Limitations |
|-----------|-------------|-------------|
| **Slack Block Kit** | Yes — `POST /slack/webhook` handles `block_actions` | No rich context view, no history, no bulk actions |
| **Admin API** | Yes — `GET /admin/review-queue`, `POST /admin/review-queue` | No UI, requires manual curl/API calls |
| **Streamlit admin UI** | In development — `ops-ui/app.py` | Not yet connected to review queue endpoints |

### Requirements

1. Three interfaces for the review queue: Slack (instant actions), Admin API (programmatic), Streamlit admin UI (dashboard).
2. Backend provides REST endpoints that serve as the canonical source of truth.
3. Streamlit UI is a separate Python application that consumes the Admin API.
4. Audit trail per decision: who, what, when, why.
5. Notification on new pending requests (Slack and/or dashboard badge).
6. SLA tracking: time-to-decision metric per operator and per workflow type.
7. History view: past decisions searchable by vendor, document, or operator.

## Decision

### Primary Decision: Review Queue as a Product Surface with Three Interfaces

The review queue is a first-class product surface with three access patterns:

```
┌─────────────────────────────────────────────────────────────┐
│                     Review Queue Backend                      │
│                  (Go, internal/adapters/http/)                │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐    │

│  │  GET /admin/review-queue/:id  — Get request detail    │    │
```

When an operator clicks a button:
1. Slack sends a `block_actions` payload to `POST /slack/webhook`.
2. The webhook handler parses the action and delegates to the Admin API logic.
3. Slack message is updated to show the decision status (e.g., "✅ Approved by @operator").
4. An audit event is recorded.

### Streamlit Admin UI

The Streamlit UI (`ops-ui/app.py`) is a separate Python application that consumes the Admin API. It provides:

```
Review Queue Dashboard
├── Pending Requests (default view)
│   ├── Table: ID, Workflow, Tier, SLA remaining, Created
│   ├── Filters: workflow, tier, status, date range
│   ├── Sort: by SLA expiry (urgent first), by created date
│   └── Row actions: Approve, Reject, View Details
│
├── Request Detail View
│   ├── Full context: vendor info, risk score, validation results, documents
│   ├── Decision form: approve/reject + reason text field
│   └── History: past decisions for this vendor/document
│
├── History View
│   ├── Table: ID, Workflow, Decision, Actor, Timestamp, Reason
│   ├── Search: by vendor, document, actor, date range
│   └── Export: CSV download
│
└── Metrics View
    ├── Avg time-to-decision (overall + by workflow)
    ├── P50/P95/P99 SLA adherence
    ├── Pending queue size over time (line chart)
    └── Operator performance (decisions per day, avg decision time)
```

The Streamlit app is deployed separately from the Go backend. It connects to the Admin API via HTTP:

```python
# ops-ui/app.py
import streamlit as st
import requests

API_BASE = st.secrets.get("API_BASE", "http://localhost:8080")

def list_pending():
    resp = requests.get(f"{API_BASE}/admin/review-queue?status=PENDING",
                        headers={"Authorization": f"Bearer {st.secrets['API_KEY']}"})
    return resp.json()

st.title("Review Queue")
for item in list_pending():
    col1, col2, col3 = st.columns([3, 1, 1])
    with col1:
        st.write(f"**{item['workflow']}** — {item['context']['vendor_name']}")
        st.caption(f"SLA expires: {item['sla_expires_at']}")
    with col2:
        st.button("Approve", key=f"approve-{item['id']}")
    with col3:
        st.button("Reject", key=f"reject-{item['id']}")
```

```json
    "workflow": "vendor_onboarding",
    "tenant_id": "tenant-xyz",
    "timestamp": "2026-07-13T10:30:00Z"

```

The Streamlit UI displays this history in the History view. Operators can search by vendor or document to see all past decisions for that entity.

### SLA Tracking

The `time-to-decision` metric is computed per HITLRequest:

```sql
-- Time to decision for a specific request
SELECT id, workflow, tier,
       EXTRACT(EPOCH FROM (decided_at - created_at)) AS decision_seconds,
       decided_by
FROM hitl_requests
WHERE status IN ('APPROVED', 'REJECTED')
  AND created_at > NOW() - INTERVAL '30 days';
```

The `/admin/review-queue/metrics` endpoint exposes:
- `avg_time_to_decision_seconds` — overall average
- `p50_time_to_decision`, `p95_time_to_decision`, `p99_time_to_decision` — percentiles
- `by_workflow` — breakdown by workflow type
- `by_operator` — breakdown by operator
- `pending_count` — current queue depth
- `sla_breach_count` — number of requests that expired SLA in the current period

### Notification on New Pending Requests

When a new HITL request is created (by any agent), the system:
1. Persists the request in the DB.
2. Sends a Slack notification with the request context and action buttons.
3. If the Streamlit UI is configured, it polls the Admin API every 30 seconds for new pending requests and shows a badge count in the browser tab title.

```python
# In Streamlit UI (client-side refresh)
st.set_page_config(page_title="Review Queue (3 pending)")
st.markdown(f'<meta http-equiv="refresh" content="30">', unsafe_allow_html=True)
```

## Alternatives Considered

### 1. Slack-Only Interface

Rejected because:
- Slack messages are ephemeral — operators may not see a request if they were offline when it was sent.
- No history or search — finding a past decision requires scrolling through Slack history.
- No bulk actions — each request must be handled individually.
- No metrics — Slack does not expose time-to-decision analytics.
- Slack is a dependency — if Slack is down, the review queue is inaccessible.

### 2. Streamlit-Only Interface

Rejected because:
- Requires operators to proactively visit the dashboard. No push notifications.
- Slack is where operators already spend their time. Adding a separate dashboard creates context switching.
- Streamlit requires network access to the Streamlit server. Slack is accessible from mobile.

### 3. Dedicated React/Django Admin Panel

Rejected because:
- Overengineering for the current scale. Streamlit provides a functional dashboard with minimal code.
- OpsCore's philosophy is to use Streamlit for admin/ops UIs (explicit in tech stack).
- A separate React app would require a full development and deployment pipeline.

### 4. No Backend REST Endpoints (Streamlit Direct DB Access)

Rejected because:
- Streamlit should not have direct database access — this violates the hexagonal architecture.
- The backend REST endpoints provide access control, validation, and audit logging.
- Direct DB access would bypass the Go application's business logic and permissions.

## Consequences

### Benefits

1. **Three interface choices.** Operators can use Slack for instant actions, Streamlit for dashboard review, or the Admin API for programmatic access. Each interface is independent — if one is down, the others still work.

2. **Canonical backend API.** All review queue logic (validation, state transitions, audit, metrics) lives in the Go backend. The UI is a thin client that consumes the API.

3. **Audited decisions.** Every approve/reject action is recorded with actor, role, reason, and timestamp. Compliance audits can trace exactly who made which decision and why.

4. **Measurable operator performance.** Time-to-decision metrics identify bottlenecks, training needs, and SLA compliance. Operators can see their own performance compared to team averages.

5. **History is searchable.** Past decisions for a vendor or document are available in the history view. Operators can see the full decision trail without searching through Slack archives.

6. **Streamlit as thin UI layer.** The Streamlit app is < 200 lines of Python. It does not contain business logic — it only displays data from the Admin API and sends actions back.

### Trade-offs / Risks

1. **Slack message update on decision requires API call.** After an operator approves via Slack, the message must be updated to reflect the decision. This requires a second Slack API call (`chat.update`). If Slack is slow, the operator may see a stale message. Mitigation: the webhook handler updates the message synchronously before returning the 200 OK to Slack.

2. **Streamlit polling adds load.** The Streamlit UI polls `/admin/review-queue` every 30 seconds. At 100 concurrent operators, this is 3.3 requests/second — negligible for the Go backend. Mitigation: add a 10-second `max-age` cache header on the response. The Go handler returns `304 Not Modified` if no new requests exist.

3. **Operator authentication.** The Admin API must authenticate operator requests. Slack actions are authenticated via Slack's signing secret. Admin API requests use a bearer token. Streamlit uses the same bearer token, stored in `st.secrets`. Mitigation: implement API key authentication for the Admin API. For production, integrate with Google OAuth or Slack OAuth.

4. **Streamlit session state.** Streamlit re-runs the script on every interaction. The pending request list is refetched on every button click. Mitigation: use `@st.cache_data` with a 10-second TTL for the pending list. The decision action is a write operation that invalidates the cache.

5. **SLA tracking accuracy if operators use multiple interfaces.** If an operator receives a Slack notification but opens the Streamlit UI to review details before approving, the SLA timer starts at request creation, not at the Streamlit interaction. Mitigation: SLA timer is based on request creation time, consistent across all interfaces.
